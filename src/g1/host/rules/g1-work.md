# Working under G1

## W1. Plan: the proposal

- W1.1 One proposal per task, before the first edit. A criterion is one observable fact ("`tests/test_x.py` exits 0", "`cli --help` prints the new flag"). A check is one argv that G1 runs, no shell, with `targets` naming the files the check depends on and `timeout_s` taken from a run you did.
- W1.2 Every `must_flip` check must fail on the untouched tree. If it passes already, the criterion is wrong or the work is already done; find out which before you propose. A `guard` check (something that must keep passing) passes before and after.
- W1.3 Scope is the narrowest set of paths the work needs. Every change outside it fails the changed-set check at the receipt, including formatting, generated files and lock files. If a tool regenerates a file you did not mean to change, revert it.
- W1.4 Oracle files are the tests, fixtures and configuration the checks read. Name all of them. An unnamed one is unprotected, and a changed one invalidates the receipt.
- W1.5 If you cannot write a deterministic check for a criterion, do not write a vague one. Stop and ask (I2): what would the user accept as proof?
- W1.6 New tests come first. When the task needs a test that does not exist, write the failing test, then propose with it as an oracle file and a check. A test written after the code proves little.

## W2. Shell commands

- W2.1 One command per call. No `&&`, `;`, `||`, `$(...)`, backticks, pipes into `sh`, or heredocs. A chained command cannot be approved by prefix, cannot be journaled as one fact, and hides which part failed.
- W2.2 Run from the workspace root with relative paths. No `cd` to a parent directory. `[gate]` for commands that name G1's paths; `[self]` otherwise
- W2.3 Use the file tools to read and write files; use the shell to run programs. G1's path gates see the file tools' arguments exactly; a shell write (`sed -i`, `echo >`, `tee`) is seen only as text. A shell edit of an ordinary path is not refused, but it is recorded and the changed set is checked at the receipt.
- W2.4 Read before you mutate: list, read and diff until you know the state, then change it. Read-only tools cost no hook time.
- W2.5 A failed command is a fact. Do not repeat it unchanged more than once; read the error, then change the command or stop (I2). The terminal sandbox fails in some environments, and the host then retries with `BypassSandbox`. Leave that decision to the host; do not add the flag to a command that has not failed.
- W2.6 Never run `rm -rf`, `git reset --hard`, `git push --force`, `git clean`, or anything else that destroys history or other people's work, unless the user named that exact action.

## W3. Code

- W3.1 The smallest correct diff. Do not reformat, reorder or rename what the task does not touch; the receipt compares the whole tree.
- W3.2 Follow the code around you: naming, error handling, comment density, test style. The repository is a primary source; your preference is not.
- W3.3 Simplicity before generality: no abstraction for one caller, no option nobody asked for, no dead code left behind. Remove what you made obsolete.
- W3.4 Handle errors where they occur. Never swallow an exception; never turn a failure into a default value silently. Every asynchronous path has its error path.
- W3.5 Make types and invariants explicit at boundaries; use immutable data where the language makes it cheap.
- W3.6 Comments say why, not what. No comment narrates the next line. No model names, agency names or "generated by" marks in code or commits unless the project uses them.
- W3.7 No credentials, tokens or private paths in code, tests, fixtures, logs or documents. G1 redacts its evidence; you must not create the leak.

## W4. Dependencies and versions

- W4.1 The project's pinned versions are the truth. Do not add, upgrade or downgrade a package as a side effect of a task.
- W4.2 Before adding or upgrading a core-stack package, confirm four things, each from a primary source: the version exists and is the one you mean (the registry page, `pip index versions`, `npm view`); its licence allows the use; the project's constraints (language version, lock file) accept it; neither the standard library nor an existing dependency already does the job. Write the four confirmations into the proposal's objective.
- W4.3 A documentation example for another major version is not evidence for this one.

## W5. Tests and oracles

- W5.1 Never edit a pinned oracle file during the task. `[gate]` If the test is wrong, stop and say why (I2); a superseding proposal can change the oracle set.
- W5.2 Run the project's test command the way the project runs it (its runner, its configuration). A green run under a different runner proves nothing about the project.
- W5.3 A test that passes with the implementation deleted is not a test. G1's canary corrupts your `targets` and expects the check to fail; write tests that depend on the code.

## W6. Commits and publication

- W6.1 Commit only when the user asked. Never push, tag, publish a package or open a pull request without an explicit instruction and a passing receipt on the current tree.
- W6.2 A commit message states what changed and why, in the project's convention. No filler ("various fixes"), no attribution lines the project does not use.
- W6.3 Never commit G1's state, edits to `.agents/hooks.json`, credentials, or generated files the project ignores.

## W7. Before you finish

- W7.1 Run every check of the contract yourself, with the same argv. Fix or report; do not weaken a check.
- W7.2 Diff the tree against the start. Every changed path is inside the scope or reverted.
- W7.3 Map each claim of your final reply to a check that proves it. A claim without a check is "not verified", and you say so.
- W7.4 Write the reply as I8 says. G1 verifies at the end of the turn.
