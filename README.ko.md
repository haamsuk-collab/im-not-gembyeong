# im-not-gembyeong

제미나이, 더 이상 젬병이 아니(고 싶)다.

젬병은 "그 일에 영 서툴다"는 말인데, 발음이 제미나이와 닮았습니다. Gemini, show the receipt.

English version: [README.md](README.md)

코드와 명령어, 문서 안에서는 이 프로그램을 G1이라고 부릅니다. 이것도 말장난입니다. Antigravity가 없앤 중력(g)을 하나
돌려놓는다는 뜻입니다. G1은 Gemini가 코드를 고치는 동안 Antigravity CLI(`agy`) 옆에서 같이 돌아가는 작은 프로그램으로, 하는
일은 두 가지입니다. 에이전트가 "다 됐다"고 하면 정말 다 됐는지 직접 확인하고, 세션이 끝나도 작업 상태가 사라지지 않게
지킵니다. 표준 라이브러리만 쓰는 Python 약 4,700줄(`wc -l` 기준)이고, 의존성은 없으며, 프로젝트 폴더 안에는 아무것도 쓰지
않습니다.

한 번만 설치하면 됩니다. 그 뒤로는 어떤 프로젝트에서든 알아서 동작합니다.

## 어떤 문제를 푸는가

"완료했습니다. 테스트가 통과합니다."

이 한 문장이 틀릴 수 있는 방식은 두 가지이고, 둘 다 실제로 재 봤습니다. 도구 호출을 일부러 막아 놓은 상태에서도 Gemini 3.8
Flash는 8번 중 3번 "DONE"이라고 답했습니다. 아무것도 못 했는데도 말입니다(`research/agy-hooks/`). 또 세션이 끝나면 에이전트의
기억도 같이 끝납니다. 다음 세션은 뭘 했는지, 뭐가 남았는지, 애초에 "완료"가 무슨 뜻이었는지도 모른 채 처음부터 다시
시작합니다.

에이전트가 스스로 "완료"라고 선언하는 건 학생이 자기 답안지를 직접 채점하는 것과 다를 게 없습니다. G1은 그 채점을 가져옵니다.
완료 조건을 작업 전에 받아 두고, 검사를 직접 돌리고, 결과를 아무도 손댈 수 없는 장부에 적습니다.

## 네 가지 핵심 개념

| 개념 | 코드에서는 |
|---|---|
| **계약(contract)** | "완료"의 정의를 작업 전에 적어 둔 것입니다. 목표, 기준, 검사, 에이전트가 고쳐도 되는 경로(`allowed_paths`), 검사가 읽는 파일(`oracle_files`)로 이루어지고, 장부의 `contract_registered` 기록 안에 통째로 들어갑니다. |
| **영수증(receipt)** | `verification_succeeded` 기록입니다. G1이 직접 돌린 검사와 종료 코드, 트리 해시, 환경 해시, 바뀐 파일 목록이 들어 있습니다. 완료 판정은 이 기록의 순번과 해시에 묶입니다. |
| **장부(ledger)** | 추가만 되는 JSONL 파일입니다. 모든 기록이 바로 앞 기록의 SHA-256을 담고 있어서 한 줄만 바뀌어도 티가 납니다. `~/.g1/workspaces/<id>/`에 있습니다. |
| **상태 블록(projection)** | G1이 모델의 문맥에 끼워 넣는 짧은 상태 요약입니다. 세션 시작 때 1,024바이트, 모델 호출 직전마다 512바이트이고, 재료는 장부뿐입니다. |

G1의 나머지 부품은 전부 이 넷을 만들거나 지키는 용도입니다.

## 어디에 끼어드는가

`agy`는 에이전트를 루프로 돌립니다. 모델을 부르고, 모델이 요청한 도구를 실행하고, 이걸 반복하다가 멈춥니다. 이 루프의 정해진
지점마다 외부 명령을 하나 실행할 수 있는데, 그 명령은 stdin으로 JSON을 받아 stdout으로 JSON을 돌려줍니다. 이 지점을
훅(hook)이라고 부릅니다. G1은 `~/.gemini/config/hooks.json`에 `g1`이라는 그룹으로 훅 네 개를 등록합니다.

| 이벤트 | 언제 | G1이 하는 일 | 제한 시간 |
|---|---|---|---|
| `SessionStart` | 대화가 시작될 때 한 번(서브에이전트 포함) | 처음 보는 프로젝트면 등록합니다. 장부를 앵커와 맞춰 보고, `agy` 바이너리가 바뀌지 않았는지 확인하고, 자기 규칙 파일이 손상됐으면 되돌린 다음 상태 블록을 넣어 줍니다. | 30초 |
| `PreInvocation` | 모델을 부르기 직전마다 | 대기 중인 제안서를 검증하고(한 번에 red baseline 최대 두 개), blocked와 resume 보고를 반영하고, 512바이트 상태 블록을 넣어 줍니다. | 900초 |
| `PreToolUse` | 쓰기 도구가 실행되기 직전 | 호출을 저널에 적습니다. G1 자신의 파일, 대화 기록, 고정된 oracle 파일, 허용 범위 밖 경로에 쓰려는 호출은 거부하고, G1의 상태를 건드리거나 G1 명령을 실행하려는 셸 명령도 거부합니다. | 20초 |
| `Stop` | 에이전트가 멈출 때 | 코드 사본에서 계약의 검사를 돌리고, 카나리아 검사를 하고, 트리를 비교한 뒤 영수증을 씁니다. 그리고 완료, 한 턴 더, 보류 중 하나로 판정합니다. | 1800초 |

`PreToolUse`에는 쓰기 도구 이름만 고르는 정규식 matcher가 걸려 있습니다(`write_to_file`, `replace_file_content`,
`run_command`, `invoke_subagent` 등). 파일을 읽거나 검색하는 도구는 G1을 아예 띄우지 않으니, 읽기에는 비용이 들지 않습니다.

훅 하나하나는 짧은 인라인 Python 프로그램입니다. `~/.g1/g1.pyz`를 해시해서 설치할 때 고정해 둔 값과 비교하고, 다르면 종료
코드 3으로 끝납니다. 그래서 누가 G1 코드를 건드리면 그 세션이 끝날 때까지 G1은 아예 실행되지 않습니다. `agy`는 `PreToolUse`가
실패하면 거부로 처리하므로, 결과적으로 다시 설치할 때까지 쓰기 도구가 전부 막힙니다. 이 동작은 측정으로 확인했고, 일부러
이렇게 두었습니다.

## 과제 하나를 처음부터 끝까지 따라가 보면

프로젝트에 잘못 구현된 `median()` 함수와 그 때문에 실패하는 테스트가 있습니다. 사용자는 "src/stats.py를 고쳐서
tests/test_stats.py를 통과시켜"라고만 했고, G1 얘기는 아무도 꺼내지 않았습니다.

1. **세션 시작.** G1에게는 처음 보는 프로젝트입니다. `~/.g1/workspaces/<경로의 sha256>/`에 genesis 기록 하나로 장부를
   만들고, 이런 내용을 넣어 줍니다. *진행 중인 계약 없음. 오래 남겨야 할 작업이면 `.../proposals/<id>.json`에 제안서를
   쓰시오.* 제안서 형식은 `views/PROPOSAL_FORMAT.md`와 설치된 스킬에 적혀 있습니다.

2. **제안서(proposal).** 에이전트가 JSON 파일 하나를 씁니다.

   ```json
   {
     "task": "fix-median",
     "objective": "median() returns the middle value for odd-length lists",
     "criteria": [{"id": "C1", "text": "tests in tests/test_stats.py pass"}],
     "checks": [{"id": "K1", "argv": ["python3", "-m", "pytest", "tests/test_stats.py", "-q"],
                 "kind": "must_flip", "covers": ["C1"], "targets": ["src/stats.py"], "timeout_s": 120}],
     "allowed_paths": ["src/"],
     "oracle_files": ["tests/test_stats.py"]
   }
   ```

3. **검증, 다음 모델 호출 직전에.** G1은 파일 이름을 `fix-median.running.json`으로 바꾸고 락을 잡은 뒤, 그 descriptor로만
   읽습니다. 이름으로 다시 열지 않기 때문에 에이전트가 중간에 내용을 바꿔치기할 수 없습니다. 그다음 이 순서로 확인합니다.
   - 형식. 엄격합니다. 모르는 키가 하나라도 있으면 제안서 전체를 거부합니다. id는 `[A-Za-z0-9][A-Za-z0-9_-]{0,63}` 형식,
     설명문은 600자 이하, 검사는 64개 이하, 경로는 상대 경로여야 하고 `.`과 `..`은 쓸 수 없습니다.
   - 커버리지. 기준마다 검사가 하나 이상 있어야 하고, 검사마다 기준을 하나 이상 덮어야 합니다. 사람이 눈으로 봐야만 확인되는
     기준은 검사가 없는 셈이므로 거부합니다.
   - 대상 파일. `must_flip` 검사는 자기가 의존하는 파일을 전부 적어야 합니다. 이 파일들은 `allowed_paths` 안에 있어야 하고,
     oracle 파일이면 안 됩니다.
   - 상태. 이 프로젝트에 진행 중인 다른 계약이 없어야 하고, `depends_on`에 적은 과제는 전부 완료 영수증이 있어야 합니다.
   - 해시 고정. oracle 파일과 검사가 부르는 실행 파일의 SHA-256을 각각 기록해 둡니다. `python3`은 에이전트의 PATH가 아니라
     깨끗한 PATH에서 찾습니다.
   - **red baseline.** 트리를 `~/.g1/scratch/baseline-*/tree`로 복사해서 검사를 전부 돌려 봅니다. `must_flip` 검사는 이
     시점에 반드시 실패해야 합니다. 작업 전부터 통과하는 검사는 작업을 증명할 수 없으니 거부합니다. `guard` 검사는 지금도,
     작업이 끝난 뒤에도 통과해야 합니다.
   - 기준 목록. 파일마다 해시, 모드, 크기를 적은 트리 전체 목록(base manifest)을 저장합니다. 나중에 어떤 파일이 바뀌었는지
     가려낼 때 씁니다.

   결과는 제안서 옆에 `fix-median.accepted.json` 또는 `fix-median.rejected.json`으로 남고, 거부 이유는 유형별로 적힙니다.
   수락되면 장부에 `contract_registered` 기록이 추가됩니다. 계약 본문, red baseline 결과, oracle 파일 해시, 실행 파일 해시,
   트리 해시가 전부 이 기록에 들어갑니다.

4. **작업.** 에이전트가 `src/stats.py`를 고치고, 테스트는 원하는 만큼 돌립니다. 파일 도구로 `tests/test_stats.py`를 고치려
   하면 `PreToolUse`가 "G1 pinned oracle"이라며 거부하고, `README.md`를 건드리면 "G1 scope"라며 거부합니다. 셸에서 `sed -i`로
   테스트 파일을 고치는 건 일부러 막지 않습니다. 에이전트가 자기 테스트를 못 돌리면 안 되기 때문입니다. 그 대신 나중에 해시
   비교에서 걸립니다.

5. **멈춤.** `agy`가 `fullyIdle: true`를 알려 오면 G1이 움직입니다. 순서는 이렇습니다.
   - 장부의 마지막 기록(head)을 앵커와 맞춰 봅니다. 어긋나면 프로젝트를 잠그고 여기서 끝냅니다.
   - oracle 파일 해시를 고정해 둔 값과 비교합니다. 다르면 `oracle_changed`로 이번 시도를 접습니다.
   - 호스트가 남긴 대화 기록에서 쓰기 도구 호출 수를 세어 자기 저널과 맞춰 봅니다(`observation_gap`).
   - 실행 파일을 다시 해시합니다(`executable_changed`).
   - 트리를 임시 폴더로 복사합니다. `.git`, `node_modules`, `.venv` 같은 폴더는 빼고, HOME과 TMPDIR은 전용으로, PATH는 허용
     목록으로, `LANG=C.UTF-8`, `PYTHONHASHSEED=0`으로 맞춥니다.
   - 그 사본에서 검사를 전부 돌립니다. 검사마다 프로세스 그룹을 따로 두고, 제한 시간과 출력 스트림당 1 MiB 상한을 겁니다.
     종료 코드 0, 시간 초과 없음, 출력 잘림 없음이면 통과입니다.
   - **카나리아(canary)** 검사. 통과한 `must_flip` 검사마다 사본을 하나 더 떠서, 그 검사의 대상 파일을 파싱할 수 없는
     바이트로 덮어쓰고 다시 돌립니다. 이번엔 반드시 실패해야 합니다. 코드가 망가져도 통과하는 검사라면 코드를 검사하는 게
     아니기 때문입니다.
   - 트리를 다시 해시합니다. 검사 전과 같아야 합니다(`identity_changed`).
   - 트리를 기준 목록과 비교합니다. 이 예에서는 `src/stats.py`만 바뀌었습니다. `allowed_paths` 밖에서 바뀐 파일이 있거나
     프로젝트 밖을 가리키는 심볼릭 링크가 새로 생겼으면 `scope_violation`입니다.
   - 증거를 `evidence/<attempt>/results.json`에 씁니다. API 키, PEM 블록, JWT, bearer 토큰은 쓰기 전에 지웁니다.
   - 장부에 `verification_started`와 `verification_succeeded`를 추가합니다.

6. **완료 판정, 락 하나 안에서.** G1은 장부 락을 잡은 채로 영수증 뒤에 다른 기록이 끼어들지 않았는지 확인하고, 트리를
   해시하고, `complete.approve()`를 호출하고, 트리를 다시 해시한 다음, compare-and-swap으로 `task_status_changed: complete`
   기록을 영수증에 묶어 추가합니다. 그 사이에 뭔가 바뀌었으면 이번 턴에는 완료하지 않고 다음 턴에 다시 검증합니다. 기록을 쓴
   뒤에도 트리를 한 번 더 해시하는데, 그 짧은 틈에 생긴 변경은 막을 수는 없지만 `post_completion_change`로 기록해서 상태
   블록에 띄웁니다.

7. 에이전트의 마지막 답변은 "median을 수정했습니다"였습니다. 이 문장은 위 과정 어디에도 입력으로 들어가지 않습니다.

## 완료 함수

`complete.approve()`는 함수 하나이고, "완료" 판정이 나올 수 있는 유일한 자리입니다. 아래 조건이 전부 맞아야 승인합니다.

- 모든 검사가 실제로 실행되어 통과, `must_flip` 검사마다 카나리아 반응 확인
- 영수증이 계약의 검사를 빠짐없이 포함(결과가 비어 있으면 "전부 통과"가 아님)
- 지금 트리 해시가 영수증의 트리 해시와 같음
- 영수증의 계약 해시가 과제의 계약 해시와 같음
- oracle 파일 해시가 고정해 둔 값과 같음
- 정책 해시(G1 버전, 코드 해시, 훅 그룹 해시)가 계약을 등록할 때 봉인한 값과 같음
- 바뀐 파일이 전부 허용 범위 안
- 관측 공백(gap)이 0
- 과제가 아직 진행 중

그 밖의 입력은 전부 거부권으로만 작동합니다. 거부 이유를 보탤 수는 있어도 승인을 보탤 수는 없습니다. 테스트 하나가 거부권
입력의 모든 조합을 돌려 보며, 실행된 증거 없이 승인이 나오는 조합이 없다는 걸 확인합니다. 에이전트가 쓴 요약을 비롯한 모델의
의견은 이 함수의 입력에 아예 없습니다.

## 검사가 통과하지 못하면

이제 G1은 에이전트를 그대로 멈추게 할지, 한 턴 더 시킬지 정해야 합니다. 이 판단을 하는 `control.decide()`는 장부만 보는 순수
함수입니다.

| 상황 | 판정 |
|---|---|
| 지난 실패 이후 트리가 그대로 | 보류, `no_change`. 검증을 돌리지 않습니다. |
| 검증 자체를 돌릴 수 없었음(oracle 파일 변경, 디스크 부족, 실행 파일 없음, 관측 공백) | 멈춤, `environment_unknown`. 진전으로도 실패로도 치지 않습니다. |
| 허용 범위 밖을 건드림 | 보류, `scope_violation` |
| 같은 트리와 같은 결과를 전에도 봤거나, 결과가 두 상태를 왔다 갔다 함 | 보류, `oscillation` |
| 이 과제에서 벌써 세 번 이어 감 | 보류, `budget_exhausted` |
| 실패하는 검사가 줄지 않음 | 보류, `no_progress` |
| 그 외 | `continue`. 통과한 검사 수, 다음에 고칠 검사, 그 검사의 정확한 명령을 한 줄로 알려 줍니다. |

이어 간 횟수는 답을 내보내기 전에 장부에 적고, 한번 적으면 줄어들지 않습니다. 검사가 뭘 출력했는지는 모델에게 그대로 보여
주지 않습니다. `agy` 자체는 세션당 열 번까지 continue를 허용하지만, G1은 과제당 세 번까지만 씁니다. 억지로 열 번 이어 가게
했을 때 답 하나 분량의 26배나 되는 토큰을 쓰면서 알맹이 없는 출력만 늘어나는 걸 봤기 때문입니다.

보류됐다고 과제가 끝난 건 아닙니다. 같은 과제 id로 새 제안서를 쓰면 red baseline을 다시 잡고 이전 계약을 대체합니다.
에이전트가 `<task>.blocked.json`(확인 못 한 항목 하나, 이유, 선택지)으로 스스로 멈춘 과제는 `<task>.resume.json`을 쓰면 같은
계약으로 이어집니다. 그 질문이 다음 세션의 상태 블록에 실리기 때문에, 새 에이전트는 짐작으로 밀어붙이는 대신 사용자에게
묻습니다.

## 기록을 믿을 수 있는 이유

**사슬.** 기록 하나는 `{"schema", "seq", "prev", "ts", "event", "data", "hash"}` 모양입니다. 정규 인코딩(UTF-8, 키 정렬, float
금지, 중복 키 금지, 꼬리 데이터 금지)으로 직렬화한 뒤 도메인 접두어를 붙여 해시합니다. 어디든 한 바이트만 바뀌어도 그 뒤의
해시가 전부 어긋납니다. `g1 audit`은 사슬을 처음부터 끝까지 걸으면서 검사별 결과로 영수증의 판정을 다시 계산하고, 완료 기록마다
완료 함수를 다시 돌려 보고, 저장된 판정이 증거보다 후하면 잡아냅니다.

**커밋.** 락(`flock`, 10초 제한, inode 재확인)을 잡은 채 이 순서로 진행합니다. 기록을 `ledger.pending.json`에 먼저 적고,
장부에 추가하고, head를 옮기고, 앵커를 옮기고, 미러에 추가하고, 먼저 적어 둔 파일을 지웁니다. 어느 단계에서 프로세스가 죽어도
다음에 장부를 열 때 먼저 적어 둔 기록으로 마무리하거나 버립니다. 줄 중간에서 끊긴 기록은 먼저 적어 둔 바이트로 채웁니다. 이미
커밋된 바이트는 절대 지우지 않습니다.

**앵커, 미러, 증인 파일.** 프로젝트의 장부 폴더 바깥에 G1은 세 가지를 따로 둡니다. 마지막으로 쓴 head를 적은 앵커(anchor,
`~/.g1/anchors/<ledger_id>.head`), 모든 기록을 복사해 둔 미러(mirror, `~/.g1/mirror/<ledger_id>.jsonl`), 이 프로젝트에 어느
장부가 속하는지 적은 증인 파일(witness, `~/.g1/anchors/ws/<id>.json`)입니다. 세션이 시작될 때와 검증에 들어가기 전마다 head와
앵커가 같은지 봅니다. 장부가 앵커보다 뒤처져 있으면 기록을 잃은 것이므로 미러에서 되살리고, 되살렸다는 사실도 기록합니다.
장부가 앵커보다 앞서 있거나 내용이 다르면 G1 바깥에서 누가 손댄 것입니다. 이때는 프로젝트를 잠가 쓰기 도구를 전부 거부하고,
사용자가 `g1 repair --accept-ledger`, `--restore`, `--forget` 중 하나를 고를 때까지 기다립니다. 되살릴 때는 앵커까지만
되살리기 때문에, 누가 미러에 몰래 덧붙인 기록이 정상 기록으로 둔갑하는 일은 없습니다.

**자기 보호.** 훅에 코드 해시가 고정돼 있다는 건 앞서 말했습니다. 세션이 시작될 때마다 규칙 파일 다섯 개와 스킬을 manifest와
대조해서 바뀐 게 있으면 되돌립니다. `agy` 바이너리의 지문(크기와 앞뒤 1 MiB의 해시)도 찍어 두는데, 바뀌었으면
`host_contract_observed: unverified`를 기록하고 사용자가 probe를 다시 돌린 뒤 `g1 host-verify`를 할 때까지 완료 판정을
보류합니다. G1의 결정 명령(`install`, `uninstall`, `init`, `propose`, `turn-end`, `host-verify`, `repair`, `challenge`,
`challenges --run`)은 `/proc`을 읽어서 조상 프로세스에 `agy`가 있으면 실행을 거부합니다. `/proc`을 읽을 수 없으면 에이전트가
실행한 것으로 간주합니다.

**에이전트의 말.** G1이 호스트의 대화 기록을 읽는 이유는 딱 하나, 모델이 실행한 쓰기 도구 호출을 세어서 자기 훅이 저널에 적은
수와 맞춰 보기 위해서입니다. 수가 다르면 관측 공백이고, 관측 공백이 있으면 완료를 거부합니다. 대화 기록이 아예 사라진 경우에는
영수증과 상태 블록에 `liveness_unknown`으로 표시만 하고 완료를 거부하지는 않습니다. 지워진 세션 때문에 새 에이전트가 작업을
이어 가지 못하면 안 되기 때문입니다.

## 게이트, 그리고 일부러 열어 둔 곳

게이트(gate)는 전부 결정적으로 동작하고 각각 이름이 있습니다. 셸 명령의 뜻을 해석하려 드는 게이트는 없습니다.

호출 전에 거부하는 경우:

- 파일 도구로 `~/.g1` 아래, hooks 파일, G1 규칙과 스킬, 프로젝트의 `.agents/hooks.json`에 쓰려는 경우. 프로젝트의
  `proposals/`와 `challenges/`는 에이전트가 쓰라고 있는 자리라 예외입니다.
- 파일 도구로 `agy`의 대화 저장소나 `.system_generated` 폴더 아래에 쓰려는 경우.
- 계약이 진행 중인데 파일 도구로 oracle 파일이나 `allowed_paths` 밖에 쓰려는 경우.
- 위 경로를 언급하거나 G1 명령줄을 실행하는 셸 명령. `g1`, `g1.pyz`, `python -m g1`, `python -c 'import g1'`을 다 잡고,
  `sudo`, `env`, `exec`, `nice`, `timeout`, `sh -c`, `eval`, here-document 뒤에 숨겨도 잡습니다. 하위 명령이 뭐든 상관없습니다.
  앞 16 KB는 `shlex`로 토큰화하고 나머지는 선형 패턴으로 훑으며, 1 MiB가 넘는 명령은 보지도 않고 거부합니다.
- 무결성 잠금 이후의 모든 쓰기 도구.

일부러 거부하지 않는 게 하나 있습니다. 셸로 일반 파일이나 oracle 파일을 고치는 것입니다. 에이전트가 자기 테스트를 못 돌리면
안 되기 때문입니다. 어차피 영수증을 쓸 때 oracle 파일 해시까지 포함해서 트리 전체를 다시 재므로, 그 수정은 거기서 걸립니다.
텍스트 게이트는 경보 장치에 가깝고, 진짜 경계는 해시 비교, 앵커 비교, 그리고 에이전트가 띄운 프로세스를 명령줄 스스로 거부하는
장치입니다.

## 두 번째 모델을 검토자로 쓰기

모델이 한 검토도 결국 주장입니다. 그래서 G1은 검토자의 지적을 한 가지 형식으로만 받습니다. **이의(challenge)**는
`challenges/<id>.json` 파일에 주장 하나와 계약 하나를 담은 것으로, 그 계약의 `must_flip` 검사는 지금 트리에서 바로 그 결함
때문에 실패해야 합니다. 검토자는 보통 다른 계열의 모델이고, 별도의 `agy` 세션에서 돌아갑니다.

이의에 든 검사는 훅 안에서 실행되지 않습니다. 사용자가 `g1 challenges .`로 목록을 보고(파싱만 하고 실행은 안 하며, 검사마다
argv 전체를 보여 줍니다), 명령을 읽어 본 다음, `g1 challenges . --run`으로 자기 권한으로 실행합니다. 검사마다 60초가
주어집니다. 실제 트리를 실행 전후로 해시해서, 트리를 건드린 검사가 있으면 그 이의는 `invalid`가 됩니다. 검사가 전부 실패하면
`confirmed`, 하나라도 통과하면 `unproven`입니다. `confirmed`가 된 이의는 사용자의 결정을 기다립니다. `g1 challenge . <id>
accept`는 red baseline을 다시 잡고 결정과 계약을 기록 하나로 등록하며, `reject`는 이유를 남깁니다. 결정을 사용자에게 맡기는
이유는, 실패하는 검사가 증명하는 건 "그 동작이 없다"는 사실이지 "검토자의 기대가 옳다"는 사실이 아니기 때문입니다. 수락하고
나면 나머지는 보통 작업과 같습니다. 작업 모델이 고치고, G1이 검증하고, 영수증으로 완료가 확정됩니다.

이 흐름을 끝까지 한 번 재 봤습니다. Flash가 SemVer 라이브러리를 만들었고(숨겨 둔 검사 44개 중 43개 통과), Claude Opus 5.5가
빠진 하나를 실패하는 검사로 73초 만에 증명했으며 거짓 보고는 없었습니다. 사용자가 수락하자 Flash가 영수증 아래에서
고쳤습니다(44개 중 44개).

## 설치

```sh
git clone https://github.com/haamsuk-collab/im-not-gembyeong ~/src/g1
~/src/g1/bin/g1 install
```

이 두 줄은 사용자가 직접 입력해야 합니다. installer는 결정 명령이라 `/proc`을 읽어 조상 프로세스에 `agy`가 있으면 종료 코드
3으로 거부합니다. 에이전트에게 설치를 시키면 거부 이유 한 줄만 받고, 결국 사용자에게 부탁하게 됩니다.

installer가 쓰고 그 뒤로 계속 지키는 파일:

| 경로 | 역할 |
|---|---|
| `~/.g1/g1.pyz` | G1 코드. bytecode만 담은 zipapp이며 표준 라이브러리만 쓰고 의존성이 없습니다. 소스 컴파일을 건너뛰어 훅당 15~25 ms를 아낍니다. |
| `~/.g1/manifest.json` | 코드 해시, 훅 그룹과 그 해시, 호스트 지문, 설치한 규칙 파일들의 해시 |
| `~/.gemini/config/hooks.json`의 `g1` 그룹 | 훅 항목 네 개. 각각 코드 해시가 고정돼 있고, 다른 도구가 넣은 항목은 바이트 그대로 둡니다. |
| `~/.gemini/config/rules/g1.md`, `g1-instinct.md` | 항상 켜져 있는 규칙 둘. 진입 규칙(권위의 순서, 다섯 가지 의무, 동작 방식)과 본능 규칙(확인하거나 멈추기, 채널별 권위, 증거, 정직한 마지막 답) |
| `~/.gemini/config/rules/g1-work.md`, `g1-writing.md`, `g1-korean.md` | 상황별 규칙. 코딩 전, 문서 작성 전, 한국어로 쓰기 전에 모델이 읽습니다. |
| `~/.gemini/config/skills/g1/SKILL.md` | 제안서 형식의 항목별 설명, blocked와 resume 보고, 이의 제기, Stop에서 G1이 하는 일 |
| `~/.g1/workspaces/<id>/` | 프로젝트마다 하나씩, 첫 세션에 만들어집니다. `ledger.jsonl`, `ledger.head.json`, `proposals/`, `challenges/`, `evidence/`, `views/` |
| `~/.g1/anchors/`, `mirror/`, `observe/`, `scratch/` | 앵커와 증인 파일, 장부 미러, 훅 저널과 잠금 표시, 검사용 임시 사본 |

프로젝트 안에는 아무것도 쓰지 않습니다. 프로젝트의 `.agents/hooks.json`에 G1 그룹이 이미 있었다면 installer가 지웁니다. 훅
층은 전역 hooks 파일 하나뿐입니다. 두 층을 두어 봤더니 비용이 두 배가 되고, 두 층이 서로 다른 호출을 보는 문제까지 있었습니다.
누가 훅 항목이나 규칙이나 스킬을 바꾸면 다음 세션에서 되돌립니다. `~/src/g1/bin/g1 uninstall`은 G1 항목만 지우고, `--purge`를
붙이면 `~/.g1`까지 지웁니다.

아래 명령은 전부 선택 사항입니다.

```sh
~/src/g1/bin/g1 status .       # G1이 아는 이 프로젝트의 상태: head, 진행 중인 과제, alert, 과제 목록
~/src/g1/bin/g1 audit .        # 사슬을 걸으면서 모든 영수증과 완료를 다시 계산
~/src/g1/bin/g1 repair .       # 잠금 뒤: 뭐가 다른지 본 다음 --accept-ledger, --restore, --forget
~/src/g1/bin/g1 challenges .   # 이의 목록. --run [ID ...]을 붙이면 그 검사를 사용자 권한으로 실행
~/src/g1/bin/g1 challenge . ID accept|reject [REASON]
~/src/g1/bin/g1 host-verify    # 새 agy 버전에서 probe를 다시 돌린 뒤
~/src/g1/bin/g1 turn-end .     # Stop 훅이 하는 일을 손으로 한 번 실행
```

launcher는 설치된 archive를 우선 쓰고, 없으면 소스 트리를 씁니다. `install`만은 항상 옆에 있는 소스 트리에서 빌드합니다.

## 비용은 얼마나 드는가

gemini-3.8-flash-high로 실제 `agy` 세션 137개를 돌려 봤습니다(그중 하나는 Claude Opus 5.5가 검토자). 아래 숫자는 전부 독립된
판정기가 낸 것입니다. 실행기가 최종 트리에서 원래 테스트를 다시 돌리거나 트리를 직접 들여다봤고, G1도 에이전트도 결과에
관여하지 않았습니다.

| 질문 | 답 |
|---|---|
| G1 때문에 에이전트가 느려지는가 | 쓰기 도구 호출 75 ms(그중 G1 자체 작업은 5 ms), 모델 호출 96 ms, 읽기 전용 호출 0 ms. 검증은 턴당 한 번, 0.3~1.1초 |
| 판정은 맞는가 | 46세션 중 46세션에서 G1의 "완료"가 판정기와 일치. 거짓 완료 없음 |
| 일이 줄어드는가 | 쉬운 과제와 중간 과제: 토큰 17~24% 감소, 시간 23~32% 감소. 어려운 단일 세션 과제: 차이 없음 |
| 세션이 날아가면 | 세션을 죽이고 기록을 지운 뒤, 다음 세션이 토큰 39% 적게, 도구 호출 33번 대신 14번으로 마침. 과제를 다시 찾아낼 필요가 없었음 |
| 두 번째 모델이 Flash가 놓친 걸 찾는가 | 한 번 끝까지 측정, 위에 적은 대로 |
| 본능 규칙이 행동을 바꾸는가 | 모호하거나 불가능한 과제 여섯 개에서 Flash는 규칙이 있을 때 12세션 중 12세션, 없을 때도 12세션 중 12세션 멈추고 물었음. 이 부류에서는 효과가 측정되지 않았고, 비용도 측정되지 않음 |

재지 못한 것도 있습니다. 과제가 작고 테스트가 눈에 보이는 경우에는 Gemini 3.8 Flash가 60세션 내내 한 번도 실패하거나
거짓말하지 않았습니다. 심판이 정말 필요한 큰 저장소와 며칠짜리 작업은 아직 이 데이터에 없습니다. 자세한 내용과 한계는
`docs/design.md` 14절과 `research/measure/`에 있습니다.

## 사람들은 무엇을 불평하는가

뭐가 잘못되는지 짐작으로 정하고 싶지 않아서, Threads와 X에서 Gemini 얘기가 나온 글 909개를 읽었습니다(한국어와 영어, 검색어
187개, 2023년 12월부터 2026년 10월까지). 그중 343개가 글쓴이 본인의 불만이었습니다. 대부분은 G1이 어떻게 할 수 없는 영역입니다.
멍청해졌다(99), 제품 문제(90), 장애(74), 다른 모델이 낫다(61), 요금(54). G1이 직접 답할 수 있는 네 가지, 즉 거짓 보고, 지시
무시, 맥락 상실, 반복은 343개 중 57개에서, 코드를 다루는 에이전트에 관한 불만 86개 중에서는 18개에서 나왔습니다. 이 숫자는
비율이 아니라 지도 정도로 봐야 합니다. 방법, 집계, 링크는 `research/complaints/`에 있습니다.

## 코드는 어떻게 검토했는가

독립된 리뷰를 다섯 번 받았습니다. 각각 `agy` 안의 Gemini 3.8 Flash 세션에 서면 지침을 주고 코드를 읽힌 것입니다. 다섯 번째
리뷰 전에는 Claude Opus 5.5와 Claude Fable 5.1이 같은 코드를 `agy` 밖에서 읽었습니다. 지적은 전부 검토자가 직접 쓴 스크립트로
재현한 뒤에 고쳤고, 고친 것마다 그 지적의 이름을 붙인 테스트가 있습니다. 다섯 번째 리뷰에서는 아무것도 나오지 않았습니다. 지침,
보고서, 답변은 `research/review/`에 있습니다. 테스트는 `tests/test_core.py`에 126개입니다.

## G1이 하지 않는 것

- 모델을 더 똑똑하게 만들지는 않습니다. 프롬프트, 도구, 에이전트 루프 어느 것도 건드리지 않습니다.
- 두 번째 모델을 심판으로 쓰지 않습니다. 모델은 설득당할 수 있지만 테스트는 그렇지 않습니다.
- `agy`의 기능을 대체하지 않습니다. 서브에이전트, goal mode, 병렬 시도는 그대로 두고 결과만 검증합니다. 서브에이전트의 도구
  호출도 자기 conversation id로 같은 훅을 거칩니다.
- 에이전트가 한 세션 안에서 셸로 G1의 파일, 앵커, 증인 파일, 미러, manifest를 전부 앞뒤 맞게 다시 써 버리면 막지 못합니다.
  G1 전체가 사용자 권한으로 돌기 때문입니다. 일부만 손댄 경우와 파일 도구로 손댄 경우는 전부 잡아내고, G1을 지운다고 거짓
  완료가 생기지도 않습니다. 완전히 막으려면 이 환경(PRoot 위의 Termux)에는 없는 OS 수준의 경계가 필요합니다. 이 잔존 위험은
  `docs/design.md` 7.7절에 적어 두었습니다.
