# im-not-gembyeong

제미나이, 더 이상 젬병이 아니(고 싶)다.

젬병은 "그 일에 영 서툴다"는 말이고 발음이 제미나이와 닮았습니다. Gemini, show the receipt.

English version: [README.md](README.md)

코드와 명령과 문서에서는 이 프로그램을 G1이라고 부릅니다. 이 이름도 말장난입니다. g 하나, Antigravity가 떼어 버린 그
중력입니다. G1은 Gemini가 코드를 고치는 동안 Antigravity CLI(`agy`) 옆에서 함께 도는 작은 프로그램입니다. 하는 일은 둘입니다.
"다 됐습니다"라는 말이 사실인지 직접 확인하고, 세션이 끝나도 작업 상태가 남게 합니다. 표준 라이브러리만 쓰는 Python 약
4,700줄(`wc -l` 기준)이고 의존성이 없으며 프로젝트 디렉터리 안에는 아무것도 쓰지 않습니다.

한 번 설치하면 그 뒤로는 모든 프로젝트에서 따로 손댈 일이 없습니다.

## 어떤 문제를 푸는가

"완료했습니다. 테스트가 통과합니다."

이 문장은 두 가지 방식으로 틀릴 수 있고, 둘 다 직접 재 보았습니다. 도구 호출을 막아 두었는데도 Gemini 3.8 Flash는 8번 중 3번
"DONE"이라고 답했습니다. 실제로는 아무것도 하지 않은 상태였습니다(`research/agy-hooks/`). 그리고 세션이 끝나면 agent의 기억도
함께 사라지므로, 다음 세션은 무엇을 했는지, 무엇이 남았는지, 애초에 "완료"가 무슨 뜻이었는지 모른 채 처음부터 시작합니다.

agent가 스스로 "완료"라고 말하는 것은 학생이 자기 답안지를 채점하는 것과 같습니다. G1은 그 채점을 대신 맡습니다. 완료 조건을
미리 받아 두고, 검사를 직접 실행하고, 결과를 아무도 고칠 수 없는 장부에 적습니다.

## 네 가지 핵심 개념

| 개념 | 코드에서의 실체 |
|---|---|
| **contract(계약)** | 작업을 시작하기 전에 적어 두는 "완료"의 정의입니다. 목표, 기준, 검사, agent가 고쳐도 되는 경로(`allowed_paths`), 검사가 읽는 파일(`oracle_files`)로 이루어지며, 장부의 `contract_registered` 기록 안에 통째로 들어갑니다. |
| **receipt(영수증)** | `verification_succeeded` 기록입니다. G1이 직접 실행한 검사와 종료 코드, 트리 해시, 환경 해시, 바뀐 경로 목록을 담습니다. 완료는 이 기록의 순번과 해시에 묶입니다. |
| **ledger(장부)** | 추가만 가능한 JSONL 파일입니다. 모든 기록이 바로 앞 기록의 SHA-256을 품고 있습니다. `~/.g1/workspaces/<id>/`에 있습니다. |
| **projection(투영)** | G1이 모델의 문맥에 주입하는 상태 블록입니다. 세션 시작 때 1,024바이트, 모델 호출 전마다 512바이트이며 장부만을 재료로 만듭니다. |

이 문서에서는 앞으로 계약, 영수증, 장부, 상태 블록이라고 부릅니다. G1의 나머지 부분은 모두 이 넷을 만들거나 지키는
장치입니다.

## 어디에 끼어드는가

`agy`는 agent를 루프로 돌립니다. 모델을 호출하고, 모델이 요청한 도구를 실행하고, 이를 반복하다가 멈춥니다. 이 루프의 정해진
지점에서 외부 명령을 실행할 수 있는데, 명령은 stdin으로 JSON을 받고 stdout으로 JSON을 돌려줍니다. 이 지점을 hook이라고
부릅니다. G1은 `~/.gemini/config/hooks.json`에 `g1`이라는 그룹으로 hook 항목 넷을 설치합니다.

| 이벤트 | 시점 | G1이 하는 일 | 제한 시간 |
|---|---|---|---|
| `SessionStart` | 대화마다 한 번(하위 agent 포함) | 처음 보는 작업 공간이면 등록합니다. 장부를 닻과 대조하고, `agy` 바이너리의 지문을 확인하고, 자기 규칙 파일이 바뀌었으면 복원한 뒤 상태 블록을 주입합니다. | 30초 |
| `PreInvocation` | 모델 호출 전마다 | 대기 중인 제안서를 검증하고(호출당 실패 기준선 최대 둘), blocked와 resume 보고를 적용하고, 512바이트 상태 블록을 주입합니다. | 900초 |
| `PreToolUse` | 쓰기 도구 실행 전 | 호출을 일지에 적습니다. G1 자신의 파일, 대화 기록, 고정된 oracle 파일, 허용 범위 밖 경로에 쓰는 호출을 거부하고, G1의 상태를 지목하거나 G1 명령을 실행하는 셸 명령도 거부합니다. | 20초 |
| `Stop` | agent가 멈출 때 | 코드 사본에서 계약의 검사를 실행하고, 카나리아 검사를 돌리고, 트리를 비교하고, 영수증을 쓴 뒤 완료, 한 턴 더, 보류 중 하나로 판정합니다. | 1800초 |

`PreToolUse`의 matcher는 쓰기 도구 이름만 고르는 정규식입니다(`write_to_file`, `replace_file_content`, `run_command`,
`invoke_subagent` 등). 파일 보기나 검색은 G1 프로세스를 띄우지 않으므로 읽기 작업에는 비용이 들지 않습니다.

hook 항목 하나하나는 짧은 인라인 Python 프로그램입니다. `~/.g1/g1.pyz`를 해시해서 설치 때 고정한 값과 비교하고, 다르면 종료
코드 3으로 끝납니다. 그래서 누군가 G1의 코드를 바꾸면 그 세션이 끝날 때까지 G1은 아예 실행되지 않고, `agy`는
`PreToolUse`의 실패를 거부로 처리하므로 다시 설치할 때까지 모든 쓰기 도구가 막힙니다. 측정으로 확인하고 의도적으로 택한
동작입니다.

## 과제 하나를 처음부터 끝까지

프로젝트에 잘못된 `median()` 함수와 실패하는 테스트가 있습니다. 사용자의 지시는 "src/stats.py를 고쳐서 tests/test_stats.py를
통과시켜"가 전부이고, G1을 언급한 사람은 아무도 없습니다.

1. **세션 시작.** G1은 이 프로젝트를 처음 봅니다. `~/.g1/workspaces/<경로의 sha256>/`에 genesis 기록 하나로 장부를 만들고,
   다음 내용을 주입합니다. *진행 중인 계약 없음. 오래 남겨야 할 작업이면 `.../proposals/<id>.json`에 제안서를 쓰시오.*
   제안서 형식은 `views/PROPOSAL_FORMAT.md`와 설치된 skill에 적혀 있습니다.

2. **제안서(proposal).** agent가 JSON 파일 하나를 씁니다.

   ```json
   {
     "task": "fix-median",
     "objective": "median() returns the middle value for odd-length lists",
     "criteria": [{"id": "C1", "text": "tests in tests/test_stats.py pass"}],
     "checks": [{"id": "K1", "argv": ["python3", "-m", "pytest", "tests/test_stats.py", "-q"],
                 "kind": "must_flip", "covers": ["C1"], "targets": ["src/stats.py"], "timeout_s": 120}],
     "allowed_paths": ["src/"],
     "oracle_files": ["tests/test_stats.py"]
   }
   ```

3. **검증, 다음 모델 호출 전에.** G1은 파일 이름을 `fix-median.running.json`으로 바꾸고 lock을 잡은 뒤, 그 descriptor를
   통해서만 읽습니다. 이름으로 다시 열지 않으므로 agent가 중간에 내용을 바꿔치기할 수 없습니다. 그다음 아래 순서로
   확인합니다.
   - 형식. 엄격하게 봅니다. 모르는 키가 하나라도 있으면 제안서 전체를 거부합니다. id는 `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`
     형식이어야 하고, 설명문은 600자 이하, 검사는 64개 이하, 경로는 상대 경로여야 하며 `.`과 `..`은 쓸 수 없습니다.
   - 커버리지 행렬. 모든 기준에 검사가 하나 이상 있어야 하고, 모든 검사는 기준을 하나 이상 덮어야 합니다. 사람이 눈으로만
     확인할 수 있는 기준은 검사가 없는 행이므로 거부됩니다.
   - 대상 파일. `must_flip` 검사는 자기가 의존하는 파일을 모두 적어야 합니다. 이 파일들은 `allowed_paths` 안에 있어야 하고
     oracle 파일이어서는 안 됩니다.
   - 상태. 이 작업 공간에 진행 중인 다른 계약이 없어야 하고, `depends_on`에 적힌 과제는 모두 완료 영수증이 있어야 합니다.
   - 해시 고정. oracle 파일 각각의 SHA-256과 검사가 부르는 실행 파일 각각의 SHA-256을 기록합니다. `python3`은 agent의
     PATH가 아니라 깨끗한 PATH에서 찾습니다.
   - **red baseline(실패 기준선).** 트리를 `~/.g1/scratch/baseline-*/tree`로 복사해 검사를 전부 실행합니다. `must_flip`
     검사는 이 시점에 반드시 실패해야 합니다. 이미 통과하는 검사는 앞으로 할 작업을 전혀 증명하지 못하므로 거부합니다.
     `guard` 검사는 지금도 통과하고 작업이 끝난 뒤에도 통과해야 합니다.
   - 기준 목록. 파일마다 해시, 모드, 크기를 적은 트리 전체의 목록(base manifest)을 저장합니다. 나중에 어떤 파일이
     바뀌었는지 가려낼 때 씁니다.

   결과는 파일 옆에 `fix-median.accepted.json` 또는 `fix-median.rejected.json`으로 남고, 거부 이유는 유형별로 적힙니다.
   수락되면 장부에 `contract_registered` 기록이 추가되는데, 계약 본문, 기준선 결과, oracle 파일 해시, 실행 파일 해시, 트리
   해시가 함께 들어갑니다.

4. **작업.** agent가 `src/stats.py`를 고치고 테스트를 원하는 만큼 실행합니다. 파일 도구로 `tests/test_stats.py`를 고치려
   하면 `PreToolUse`가 "G1 pinned oracle"이라는 이유로 거부하고, `README.md`를 건드리면 "G1 scope"로 거부합니다. 셸에서
   `sed -i`로 테스트 파일을 고치는 것은 의도적으로 막지 않습니다. agent가 자기 테스트를 실행할 수 있어야 하기 때문입니다. 그
   수정은 나중에 해시 대조에서 잡힙니다.

5. **멈춤.** `agy`가 `fullyIdle: true`를 보고하면 G1은 다음 순서로 일합니다.
   - 장부의 마지막 기록(head)을 닻과 대조합니다. 어긋나면 작업 공간을 잠그고 아무것도 실행하지 않습니다.
   - oracle 파일의 해시를 고정값과 비교합니다. 다르면 `oracle_changed`로 이번 시도를 끝냅니다.
   - 호스트의 대화 기록에 적힌 쓰기 도구 호출 수를 자기 일지와 비교합니다(`observation_gap`).
   - 실행 파일을 다시 해시합니다(`executable_changed`).
   - 트리를 임시 디렉터리로 복사합니다. `.git`, `node_modules`, `.venv` 같은 디렉터리는 제외하고, HOME과 TMPDIR은 전용
     디렉터리로, PATH는 허용 목록으로, `LANG=C.UTF-8`과 `PYTHONHASHSEED=0`으로 둡니다.
   - 그 사본에서 검사를 전부 실행합니다. 검사마다 별도 프로세스 그룹, 제한 시간, 출력 스트림당 1 MiB 상한이 걸립니다. 종료
     코드가 0이고 시간 초과와 출력 잘림이 없으면 통과입니다.
   - **canary(카나리아)** 검사를 합니다. 통과한 `must_flip` 검사마다 사본을 하나 더 만들어 그 검사의 대상 파일을 파싱할 수
     없는 바이트로 덮어쓰고 다시 실행합니다. 이번에는 반드시 실패해야 합니다. 코드가 없어도 통과하는 검사는 코드를 검사하는
     것이 아니기 때문입니다.
   - 트리를 다시 해시합니다. 검사 전의 해시와 같아야 합니다(`identity_changed`).
   - 트리를 기준 목록과 비교합니다. 이 예에서는 `src/stats.py`만 바뀌었습니다. `allowed_paths` 밖에서 바뀐 경로나 작업 공간
     밖을 가리키는 새 symbolic link가 있으면 `scope_violation`입니다.
   - 증거를 `evidence/<attempt>/results.json`에 씁니다. API key, PEM 블록, JWT, bearer token은 먼저 지웁니다.
   - 장부에 `verification_started`와 `verification_succeeded`를 추가합니다.

6. **완료 판정, lock 하나 안에서.** G1은 장부 lock을 잡고, 영수증 뒤에 다른 기록이 추가되지 않았는지 확인하고, 트리를
   해시하고, `complete.approve()`를 호출하고, 트리를 다시 해시한 뒤, compare-and-swap으로 `task_status_changed: complete`
   기록을 영수증에 묶어 추가합니다. 그 사이에 무엇이든 바뀌었으면 이번 턴에는 완료하지 않고 다음 턴에 다시 검증합니다. 기록을
   쓴 뒤 트리를 한 번 더 해시하는데, 그 짧은 틈에 생긴 변경은 막을 수 없지만 `post_completion_change`로 기록하고 상태
   블록에 표시합니다.

7. agent의 마지막 답변은 "median을 수정했습니다"였습니다. 이 문장은 위 과정 어디에도 입력으로 쓰이지 않았습니다.

## 완료 함수

`complete.approve()`는 함수 하나이고, "완료"라는 판정이 나오는 유일한 자리입니다. 아래 조건이 모두 성립할 때만 승인합니다.

- 모든 검사가 실제로 실행되어 통과했고, 모든 `must_flip` 검사의 카나리아가 민감하게 반응했습니다.
- 영수증이 계약의 모든 검사를 덮습니다. 검사 결과가 비어 있으면 "전부 통과"로 치지 않습니다.
- 현재 트리 해시가 영수증의 해시와 같습니다.
- 영수증의 계약 해시가 과제의 계약 해시와 같습니다.
- oracle 파일의 해시가 고정값과 같습니다.
- 정책 해시(G1 버전, 코드 해시, hook 그룹 해시)가 계약 등록 때 봉인한 값과 같습니다.
- 바뀐 경로가 모두 허용 범위 안에 있습니다.
- 관측 공백(gap)이 0입니다.
- 과제가 아직 진행 중(active)입니다.

이 밖의 모든 입력은 거부권(veto)으로만 작동합니다. 거부 이유를 보탤 수는 있어도 승인을 보탤 수는 없습니다. 테스트 하나가
거부권 입력의 모든 조합을 나열해, 실행된 증거 없이는 어떤 조합도 승인에 이르지 못함을 확인합니다. agent 자신의 요약을 포함한
모델의 의견은 이 함수의 입력에 없습니다.

## 검사가 통과하지 못했을 때

G1은 agent를 그대로 멈추게 할지, 한 턴 더 시킬지 정해야 합니다. `control.decide()`는 장부만 보고 판정하는 순수 함수입니다.

| 상황 | 판정 |
|---|---|
| 지난 실패 이후 트리가 바뀌지 않음 | 보류, `no_change`. 검증을 실행하지 않습니다. |
| 검증을 실행할 수 없었음(oracle 파일 변경, 디스크 부족, 실행 파일 없음, 관측 공백) | 멈춤, `environment_unknown`. 진전으로도 실패로도 치지 않습니다. |
| 허용 범위 밖 변경 | 보류, `scope_violation` |
| 같은 트리와 결과 조합을 전에 보았거나, 결과가 두 상태를 번갈아 반복함 | 보류, `oscillation` |
| 이 과제에서 이미 세 번 이어 감 | 보류, `budget_exhausted` |
| 실패하는 검사의 집합이 줄어들지 않음 | 보류, `no_progress` |
| 그 밖의 경우 | `continue`. 통과한 검사 수, 다음에 고칠 검사와 그 정확한 명령을 한 줄로 전합니다. |

이어 가기 횟수는 답을 출력하기 전에 장부에 쓰고, 이후 줄어들지 않습니다. 검사의 원본 출력은 모델 문맥에 되돌려 주지
않습니다. `agy` 자체는 세션당 열 번까지 continue를 허용하지만 G1은 과제당 세 번까지만 씁니다. 강제로 열 번 이어 가게 한
측정에서 답 하나의 26배에 이르는 토큰을 쓰면서 내용 없는 출력만 늘었기 때문입니다.

보류된 과제가 끝난 것은 아닙니다. 같은 과제 id로 새 제안서를 쓰면 실패 기준선을 새로 잡고 이전 계약을 대체합니다. agent가
`<task>.blocked.json`(확인하지 못한 항목 하나, 이유, 선택지)으로 스스로 멈춘 과제는 `<task>.resume.json`으로 같은 계약 아래
이어집니다. 다음 세션의 상태 블록에 그 질문이 실리므로, 새 agent는 추측하지 않고 사용자에게 묻습니다.

## 기록을 믿을 수 있는 이유

**사슬.** 기록 하나는 `{"schema", "seq", "prev", "ts", "event", "data", "hash"}` 꼴입니다. 정규 인코딩(UTF-8, 키 정렬, float
금지, 중복 키 금지, 꼬리 데이터 금지)으로 직렬화한 뒤 도메인 접두어를 붙여 해시합니다. 어디서든 한 바이트가 바뀌면 그 뒤의 모든
해시가 어긋납니다. `g1 audit`은 사슬을 처음부터 걷고, 검사별 결과에서 영수증의 판정을 다시 계산하고, 완료 기록마다 완료
함수를 다시 실행하며, 저장된 판정이 증거보다 후하면 지적합니다.

**commit.** lock(`flock`, 10초 제한, inode 재확인) 아래 다음 순서로 진행합니다. 기록을 `ledger.pending.json`에 미리 적고,
장부에 추가하고, head를 옮기고, 닻을 옮기고, 복제본에 추가하고, 미리 적은 파일을 지웁니다. 어느 단계에서 프로세스가 죽어도
다음에 장부를 열 때 미리 적은 기록으로 마무리하거나 버립니다. 줄 중간에서 끊긴 추가는 미리 적은 바이트로 채웁니다. 이미
commit된 바이트는 지우지 않습니다.

**닻, 복제본, 증인.** 작업 공간 디렉터리 밖에 G1은 세 가지를 둡니다. 마지막으로 쓴 head인 닻(anchor,
`~/.g1/anchors/<ledger_id>.head`), 모든 기록의 복제본(mirror, `~/.g1/mirror/<ledger_id>.jsonl`), 작업 공간마다 어느 장부가
속하는지 적은 증인(witness, `~/.g1/anchors/ws/<id>.json`)입니다. 세션 시작 때와 검증 전마다 head는 닻과 같아야 합니다. 닻보다
뒤처진 장부는 기록을 잃은 것이므로 복제본에서 되살리고 그 수리를 기록합니다. 닻보다 앞서거나 내용이 다른 장부는 G1 밖에서
바뀐 것이므로 작업 공간을 잠그고 모든 쓰기 도구를 거부하며, 사용자가 `g1 repair --accept-ledger`, `--restore`, `--forget`
중 하나로 결정할 때까지 기다립니다. 복원 범위는 닻까지로 한정하므로, 누군가 복제본에 덧붙인 기록이 정상 기록으로 돌아오는
일은 없습니다.

**자기 보호.** hook 항목이 코드 해시를 고정합니다. 세션 시작 때마다 규칙 파일 다섯과 skill을 manifest와 대조해 바뀐 것은
되돌립니다. `agy` 바이너리의 지문(크기와 앞뒤 1 MiB의 해시)을 찍고, 바뀌었으면 `host_contract_observed: unverified`를 기록한
뒤 사용자가 probe를 다시 실행하고 `g1 host-verify`를 할 때까지 완료를 보류합니다. G1의 결정 명령(`install`, `uninstall`,
`init`, `propose`, `turn-end`, `host-verify`, `repair`, `challenge`, `challenges --run`)은 `/proc`을 읽어 조상 프로세스에
`agy`가 있으면 실행을 거부합니다. `/proc`을 읽을 수 없으면 agent가 실행한 것으로 간주합니다.

**agent의 말.** G1이 호스트의 대화 기록을 읽는 목적은 하나입니다. 모델이 실행한 쓰기 도구 호출을 세어 자기 hook이 일지에 적은
수와 맞추는 것입니다. 차이가 있으면 관측 공백이고, 관측 공백은 완료를 거부합니다. 대화 기록이 사라진 경우에는 영수증과 상태
블록에 `liveness_unknown`으로 표시하되 완료를 거부하지는 않습니다. 지워진 세션 때문에 새 agent가 작업을 이어 가지 못해서는
안 되기 때문입니다.

## 관문, 그리고 일부러 열어 둔 곳

모든 관문(gate)은 결정적으로 동작하고 이름이 있습니다. 셸 명령의 의미를 해석하려 드는 관문은 없습니다.

호출 전에 거부하는 경우:

- 파일 도구로 `~/.g1` 아래, hooks 파일, G1 규칙과 skill, 작업 공간의 `.agents/hooks.json`에 쓰는 경우. 작업 공간의
  `proposals/`와 `challenges/`는 agent가 쓰는 자리이므로 예외입니다.
- 파일 도구로 `agy`의 대화 저장소나 `.system_generated` 디렉터리 아래에 쓰는 경우.
- 계약이 진행 중일 때 파일 도구로 oracle 파일이나 `allowed_paths` 밖에 쓰는 경우.
- 위 경로를 본문에 지목하거나 명령 위치에서 G1 명령줄을 실행하는 셸 명령. `g1`, `g1.pyz`, `python -m g1`,
  `python -c 'import g1'`을 모두 보고, `sudo`, `env`, `exec`, `nice`, `timeout`, `sh -c`, `eval`, here-document 뒤에 있는
  것도 봅니다. 하위 명령은 가리지 않습니다. 앞 16 KB는 `shlex`로 토큰화하고 나머지는 선형 패턴으로 훑으며, 1 MiB를 넘는
  명령은 그대로 거부합니다.
- 무결성 잠금 이후의 모든 쓰기 도구.

의도적으로 거부하지 않는 경우는 셸로 일반 파일이나 oracle 파일을 고치는 것입니다. agent는 자기 테스트를 실행할 수 있어야
합니다. 영수증을 쓸 때 oracle 파일 해시를 포함해 트리 전체를 다시 재므로, 그 수정은 결국 거기서 잡힙니다. 텍스트 관문은 경보
장치이고, 실제 경계는 해시 대조, 닻 대조, 그리고 agent가 띄운 프로세스를 명령줄 스스로 거부하는 장치입니다.

## 두 번째 모델을 검토자로

모델의 검토 결과도 다른 주장과 마찬가지로 주장일 뿐입니다. G1은 검토자의 지적을 한 가지 형식으로만 받습니다.
**challenge(이의)**는 `challenges/<id>.json` 파일에 주장 하나와 계약 하나를 담은 것으로, 그 계약의 `must_flip` 검사는 현재
트리에서 바로 그 결함 때문에 실패해야 합니다. 검토자는 보통 다른 계열의 모델이 별도의 `agy` 세션에서 맡습니다.

이의의 검사는 hook 안에서 실행되지 않습니다. 사용자가 `g1 challenges .`로 목록을 보고(파싱만 하고 실행하지 않으며, 검사마다
argv 전체를 표시), 명령을 읽은 뒤 `g1 challenges . --run`으로 자기 권한으로 실행합니다. 검사마다 60초가 주어집니다. 실제
트리를 실행 전후에 해시하고, 트리를 바꾼 검사가 있으면 그 이의는 `invalid`가 됩니다. 검사가 전부 실패하면 `confirmed`,
하나라도 통과하면 `unproven`입니다. confirmed된 이의는 사용자의 결정을 기다립니다. `g1 challenge . <id> accept`는 실패
기준선을 다시 잡고 결정과 계약을 기록 하나로 등록하며, `reject`는 이유를 기록합니다. 결정을 사용자에게 맡기는 이유는, 실패하는
검사가 증명하는 것은 "그 동작이 없다"는 사실이지 "검토자의 기대가 옳다"는 사실이 아니기 때문입니다. 수락 이후는 보통 작업과
같습니다. 작업 모델이 고치고, G1이 검증하고, 영수증이 완료를 확정합니다.

이 흐름을 끝까지 한 번 측정했습니다. Flash가 SemVer 라이브러리를 만들었고(숨은 검사 44개 중 43개 통과), Claude Opus 5.5가
빠진 하나를 실패하는 검사로 73초 만에 증명했으며 거짓 보고는 없었습니다. 사용자가 수락하자 Flash가 영수증 아래에서
고쳤습니다(44개 중 44개).

## 설치

```sh
git clone https://github.com/haamsuk-collab/im-not-gembyeong ~/src/g1
~/src/g1/bin/g1 install
```

이 두 줄은 사용자가 직접 실행해야 합니다. installer는 결정 명령이어서 `/proc`을 읽고 조상 프로세스에 `agy`가 있으면 종료
코드 3으로 거부합니다. agent에게 설치를 시키면 거부 이유 한 줄을 받고 사용자에게 요청하게 됩니다.

installer가 쓰고 그 뒤로 계속 관리하는 파일:

| 경로 | 역할 |
|---|---|
| `~/.g1/g1.pyz` | G1 코드. bytecode만 담은 zipapp이며 표준 라이브러리만 쓰고 의존성이 없습니다. 소스 컴파일을 생략해 hook당 15~25 ms를 줄입니다. |
| `~/.g1/manifest.json` | 코드 해시, hook 그룹과 그 해시, 호스트 지문, 설치한 규칙 파일들의 해시 |
| `~/.gemini/config/hooks.json`의 `g1` 그룹 | hook 항목 넷. 각각 코드 해시가 고정되어 있고, 다른 도구의 항목은 바이트 그대로 보존합니다. |
| `~/.gemini/config/rules/g1.md`, `g1-instinct.md` | 항상 켜진 규칙 둘. 진입 규칙(권위의 순서, 다섯 의무, 동작 방식)과 본능 규칙(확인하거나 멈추기, 채널별 권위, 증거, 정직한 마지막 답) |
| `~/.gemini/config/rules/g1-work.md`, `g1-writing.md`, `g1-korean.md` | 상황별 규칙. 코딩 전, 문서 작성 전, 한국어 작성 전에 모델이 읽습니다. |
| `~/.gemini/config/skills/g1/SKILL.md` | 제안서 형식의 항목별 설명, blocked와 resume 보고, 이의 제기, Stop에서 G1이 하는 일 |
| `~/.g1/workspaces/<id>/` | 프로젝트마다 하나, 첫 세션에 생성. `ledger.jsonl`, `ledger.head.json`, `proposals/`, `challenges/`, `evidence/`, `views/` |
| `~/.g1/anchors/`, `mirror/`, `observe/`, `scratch/` | 닻과 증인, 장부 복제본, hook 일지와 잠금 표시, 검사용 임시 사본 |

프로젝트 안에는 아무것도 쓰지 않습니다. 작업 공간의 `.agents/hooks.json`에 G1 그룹이 있었다면 installer가 지웁니다. hook 층은
전역 hooks 파일 하나뿐입니다. 두 층을 두었을 때 비용이 두 배가 되고 두 층이 서로 다른 호출을 보는 문제가 있었습니다. 누군가
hook 항목이나 규칙이나 skill을 바꾸면 다음 세션이 되돌립니다. `~/src/g1/bin/g1 uninstall`은 G1의 항목만 지우고, `--purge`를
붙이면 `~/.g1`도 지웁니다.

명령은 모두 선택 사항입니다.

```sh
~/src/g1/bin/g1 status .       # G1이 아는 이 프로젝트의 상태: head, 진행 중인 과제, alert, 과제 목록
~/src/g1/bin/g1 audit .        # 사슬을 걷고 모든 영수증과 완료를 다시 계산
~/src/g1/bin/g1 repair .       # 잠금 뒤: 무엇이 다른지 본 다음 --accept-ledger, --restore, --forget
~/src/g1/bin/g1 challenges .   # 이의 목록. --run [ID ...]이면 그 검사를 사용자 권한으로 실행
~/src/g1/bin/g1 challenge . ID accept|reject [REASON]
~/src/g1/bin/g1 host-verify    # 새 agy 버전에서 probe를 다시 실행한 뒤
~/src/g1/bin/g1 turn-end .     # Stop hook이 하는 일을 손으로 한 번 실행
```

launcher는 설치된 archive를 우선 쓰고, 없으면 소스 트리를 씁니다. `install`만은 항상 옆에 있는 소스 트리에서 빌드합니다.

## 측정한 비용

gemini-3.8-flash-high로 실제 `agy` 세션 137개를 돌렸습니다(그중 하나는 Claude Opus 5.5가 검토자). 아래 숫자는 모두 독립된
판정기가 냈습니다. 실행기가 최종 트리에서 원래 테스트를 다시 실행하거나 트리를 직접 확인했고, G1도 agent도 결과에 관여하지
않았습니다.

| 질문 | 답 |
|---|---|
| G1이 agent를 느리게 하는가 | 쓰기 도구 호출 75 ms(그중 G1 자체 작업은 5 ms), 모델 호출 96 ms, 읽기 전용 호출 0 ms. 검증은 턴당 한 번, 0.3~1.1초 |
| 판정이 맞는가 | 46세션 중 46세션에서 G1의 "완료"가 판정기와 일치. 거짓 완료 없음 |
| 작업량이 줄어드는가 | 쉬운 과제와 중간 과제: 토큰 17~24% 감소, 시간 23~32% 감소. 어려운 단일 세션 과제: 차이 없음 |
| 세션이 사라지면 | 세션을 죽이고 기록을 지운 뒤, 다음 세션이 토큰 39% 적게, 도구 호출 33번 대신 14번으로 마침. 과제를 다시 찾아낼 필요가 없었음 |
| 두 번째 모델이 Flash가 놓친 것을 찾는가 | 한 번 끝까지 측정, 위에 적은 대로 |
| 본능 규칙이 행동을 바꾸는가 | 모호하거나 불가능한 과제 여섯에서 Flash는 규칙이 있을 때 12세션 중 12세션, 없을 때도 12세션 중 12세션 멈추고 물었음. 이 부류에서는 효과가 측정되지 않았고 측정되는 비용도 없음 |

측정하지 못한 것도 있습니다. 과제가 자족적이고 테스트가 보이는 경우 Gemini 3.8 Flash는 60세션 동안 한 번도 실패하거나
거짓말하지 않았습니다. 심판이 가장 필요한 큰 저장소와 며칠짜리 작업은 아직 이 데이터에 없습니다. 세부와 한계는
`docs/design.md` 14절과 `research/measure/`에 있습니다.

## 사용자들의 불만

무엇이 잘못되는지 추측하는 대신 Threads와 X에서 Gemini에 관한 글 909개를 읽었습니다(한국어와 영어, 검색어 187개, 2023년
12월부터 2026년 10월까지). 그중 343개가 사용자 자신의 불만입니다. 대부분은 G1이 손댈 수 없는 영역입니다. 멍청해졌다(99),
제품(90), 장애(74), 경쟁 모델(61), 요금(54). G1이 직접 답하는 네 꼬리표, 즉 거짓 보고, 지시 무시, 맥락 상실, 반복은 불만
343개 중 57개에, 코드를 다루는 agent에 관한 불만 86개 중 18개에 나타납니다. 이 숫자는 비율이 아니라 지도로 읽어야 합니다.
방법과 집계와 링크는 `research/complaints/`에 있습니다.

## 코드 검토 과정

독립된 리뷰를 다섯 번 받았습니다. 각각 `agy` 안의 Gemini 3.8 Flash 세션에 서면 지침을 준 것입니다. 다섯 번째 리뷰 전에는
Claude Opus 5.5와 Claude Fable 5.1이 같은 코드를 `agy` 밖에서 읽었습니다. 모든 지적은 검토자 자신의 스크립트로 재현한 뒤에
고쳤고, 모든 수정에는 지적의 이름을 붙인 테스트가 있습니다. 다섯 번째 리뷰는 아무것도 찾지 못했습니다. 지침, 보고서, 답변은
`research/review/`에 있습니다. 테스트는 `tests/test_core.py`에 126개입니다.

## G1이 하지 않는 것

- 모델을 더 똑똑하게 만들지 않습니다. prompt, 도구, agent 루프를 그대로 둡니다.
- 두 번째 모델을 심판으로 쓰지 않습니다. 모델은 설득당할 수 있지만 테스트는 그렇지 않습니다.
- `agy`의 기능을 대체하지 않습니다. 하위 agent, goal mode, 병렬 시도는 그대로 두고 결과만 검증합니다. 하위 agent의 도구
  호출도 자기 conversation id로 같은 hook을 거칩니다.
- agent가 한 세션 안에서 셸로 G1의 파일, 닻, 증인, 복제본, manifest를 전부 일관되게 다시 쓰면 막지 못합니다. G1 전체가
  사용자 권한으로 실행되기 때문입니다. 부분적인 변조와 구조화된 도구를 통한 변조는 모두 잡아내고, G1을 지운다고 거짓 완료가
  생기지는 않습니다. 완전한 방어에는 이 환경(PRoot 위의 Termux)이 제공하지 않는 OS 수준의 경계가 필요합니다. 이 잔존 위험은
  `docs/design.md` 7.7절에 적혀 있습니다.
