# im-not-gembyeong

제미나이, 더 이상 젬병이 아니(고 싶)다.

젬병은 "그 일에 영 서툴다"는 말이고, 발음이 제미나이와 닮았습니다. Gemini, show the receipt.

English version: [README.md](README.md)

코드와 명령과 문서에서 이 프로그램의 이름은 G1입니다. (이 이름도 말장난입니다. g 하나, Antigravity가 떼어 버린 그 중력입니다.)
G1은 Antigravity CLI(`agy`) 옆에서 Gemini가 코드를 다루는 동안 함께 도는 작은 프로그램입니다. 하는 일은 하나입니다.
"다 됐다"가 정말 다 된 것인지 확인하고, 세션이 끝나도 일이 남게 합니다.

한 번 설치하면 그 뒤로는 모든 프로젝트에서 아무 조작 없이 동작합니다.

## 그림 하나로 시작합니다

AI 코딩 agent에게 버그 수정을 맡깁니다. 2분 뒤에 답이 옵니다. "완료했습니다. 테스트가 통과합니다."

이 문장은 두 가지로 틀릴 수 있습니다.

1. 사실이 아닐 수 있습니다. Gemini 3.8 Flash로 직접 재 보았습니다. 도구 호출을 막아 놓았는데도 8번 중 3번은 "DONE"이라고
   답했습니다. 아무것도 하지 않았는데도요.
2. 잊힐 수 있습니다. 세션이 끝나면 agent의 기억도 끝납니다. 다음 세션은 무엇을 했는지, 무엇이 남았는지, 애초에 "완료"가 무슨
   뜻이었는지 모른 채 0에서 시작합니다.

스스로 "완료"라고 말하는 agent는 자기 시험지를 자기가 채점하는 학생과 같습니다. G1은 심판입니다. 정답지를 쥐고, 시험을 직접
돌리고, 결과를 지울 수 없는 장부에 적습니다.

## Gemini가 틀릴 때 사람들이 하는 말

무엇이 잘못되는지 추측하고 싶지 않았습니다. 그래서 사용자가 하는 말을 모았습니다. 2026년 10월 12일에 Threads와 X에서 Gemini에
관한 글을 한국어와 영어로 검색했습니다. 검색어 187개로 찾은 글 909개를 읽었습니다(Threads 534개, X
375개, 한국어 336개, 영어 573개, 작성일 2023년 12월부터 2026년 10월까지). 그중 343개가 사용자 자신의 불만이었고,
각 불만에 아래 꼬리표를 하나 이상 붙였습니다.

| 불만의 내용 | 글 수 | G1의 답 |
|---|---|---|
| 멍청해짐, 전반적 실망 | 99 | 없음, G1은 모델을 바꾸지 않음 |
| 제품, 앱, 강제 통합 | 90 | 없음 |
| 오류, 속도, 장애 | 74 | 없음, 호스트의 문제 |
| Claude, GPT, Codex보다 못함 | 61 | 없음 |
| 한도, 요금, 구독 | 54 | 없음 |
| 지어낸 사실과 출처 | 39 | 사실 오류에는 없음, 코드에 관한 주장은 믿지 않고 검사함 |
| 거부, 검열, 게으른 답 | 35 | 없음 |
| 코드를 망가뜨리거나 지움, 나쁜 코드 | 25 | 고정된 테스트 파일, "완료" 전에 사본에서 검사가 통과해야 함 |
| 지시를 무시하고 관계없는 코드를 고침 | 24 | 범위가 있는 contract(계약), 범위 밖 쓰기는 거부하거나 receipt(영수증)에서 잡음 |
| 맥락을 잊고 흐름을 놓침 | 19 | ledger(장부), 모든 세션은 기억이 아니라 기록에서 시작함 |
| 반복, 무한 루프, 끝없는 생각 | 18 | 이어 가기 예산, 아무것도 바꾸지 않은 턴은 끝남 |
| 아첨, 사과, 가스라이팅 | 13 | agent의 말은 어떤 경우에도 증거가 아님 |
| 한국어 등 언어 품질 | 6 | 없음 |
| 하지도 않은 일을 끝냈다거나 검사했다고 말함 | 1 | receipt, 완료는 G1이 검사를 돌렸을 때만 존재함 |

불만 343개 중 86개는 Gemini가 코드나 파일에 여러 단계의 일을 하는 상황(Gemini CLI, Antigravity, Cursor,
"내 저장소를 고쳤다")에 관한 것입니다. 이 묶음에서 G1이 답하는 네 꼬리표, 거짓 보고, 지시 무시, 맥락 상실, 반복은
18개 글에 나타나고, 불만 343개 전체에서는 57개 글에 나타납니다.

이 표는 지도이지 점수가 아닙니다. 글은 검색 엔진이 색인한 것뿐이고, 두 플랫폼 모두 계정 없이는 검색할 수 없으므로 표본은
넓지만 완전하지 않습니다. 방법, 플랫폼과 언어별 집계, 꼬리표별 글 링크는 `research/complaints/`에 있습니다. 글 본문은 이
저장소에 넣지 않았습니다.

## 심판에게 필요한 것

과제를 공정하게 판정하려면 네 가지가 필요합니다.

| 필요한 것 | 이유 | G1의 이름 |
|---|---|---|
| 일을 시작하기 전에 적어 둔 "완료"의 정의 | 끝난 뒤에 목표를 옮길 수 없도록 | **contract(계약)** |
| 검사를 직접 돌릴 방법 | 보고는 주장일 뿐이므로 | **verification(검증)** |
| 고칠 수 없는 기록 | 역사가 그대로 남도록 | **ledger(장부)** |
| 다음 사람에게 현재 상태를 알릴 방법 | 어떤 일도 잃지 않도록 | **projection(투영)** |

G1의 모든 것은 이 넷 중 하나입니다.

## 네 순간

`agy`는 agent가 일하는 중 정해진 순간에 외부 프로그램을 실행합니다. 이 순간을 hook이라고 부릅니다. G1은 그중 넷을 씁니다.

```
세션 시작 ──► G1이 상태를 주입: "작업 X 진행 중, 검사 K2 아직 실패, 범위는 src/"
   │
   ├─ 모델 호출 전마다 ──► G1이 512바이트 상태 줄을 주입 (긴 세션도 잊지 않도록)
   │
   ├─ 파일 쓰기나 셸 명령 전마다 ──► G1이 자기 파일, 고정된 테스트 파일, 범위 밖 경로에 대한
   │                                   쓰기를 거부
   │
   └─ agent가 멈출 때 ──► G1이 contract의 검사를 코드 사본 위에서 직접 돌리고
                          receipt를 쓴 뒤 판정: 완료, 또는 아직 아님
```

읽기 전용 도구(파일 보기, 검색)는 G1을 띄우지 않으므로 비용이 없습니다.

## 과제 하나, 처음부터 끝까지

테스트에서 실제로 돌린 예입니다. 프로젝트에는 틀린 함수 `median()`과 실패하는 테스트가 있습니다. 사용자의 지시는 이것이
전부였습니다. *"src/stats.py를 고쳐서 tests/test_stats.py를 통과시켜."* G1이라는 말은 없었습니다.

1. 세션 시작. G1은 처음 보는 이 프로젝트를 등록하고 이렇게 주입합니다. *"진행 중인 contract 없음. 오래 남을 일이라면
   `.../proposals/<id>.json`에 proposal을 쓰시오."*
2. agent가 proposal(제안서)을 씁니다. 목표와 기준 하나("테스트가 통과한다"), 검사 하나(`python3 tests/test_stats.py`), 그
   검사가 의존하는 파일(`src/stats.py`), agent가 고쳐도 되는 범위(`src/`), 고정해 둘 테스트 파일(`tests/test_stats.py`)을
   적습니다.
3. G1은 다음 모델 호출 전에 proposal을 검증합니다. 형식을 확인한 뒤 손대지 않은 코드에서 검사를 돌립니다. 이 검사는 지금
   반드시 실패해야 합니다. 이미 통과하는 검사는 한 일을 전혀 증명하지 못하기 때문입니다. 이것이 **red baseline(빨간
   기준선)**입니다. G1은 테스트 파일의 해시도 기록합니다. proposal은 contract가 됩니다.
4. agent가 코드를 고칩니다. 테스트는 얼마든지 돌려도 됩니다. 테스트 파일이나 `src/` 밖의 파일을 고치려 하면 G1이 거부합니다.
5. agent가 멈춥니다. G1은 코드를 임시 디렉터리로 복사해 깨끗한 환경에서 검사를 돌립니다. 통과합니다. 그다음 두 번째 사본에서
   `src/stats.py`를 망가뜨리고 검사를 다시 돌립니다. 이번에는 반드시 실패해야 합니다. 실패하지 않는다면 그 검사는 코드와
   무관한 것입니다. 이것이 **canary(카나리아)**입니다.
6. G1은 파일 트리를 contract 때 기록한 트리와 비교합니다. `src/stats.py`만 바뀌었습니다.
7. G1은 ledger에 receipt를 쓰고 과제를 완료로 표시합니다. agent의 마지막 말은 "median을 수정했습니다"였습니다. 그 말은 이
   판정의 입력이 아니었습니다.

5단계가 실패했다면 G1은 이유를 기록하고, 지난번보다 실패한 검사가 줄었을 때만 agent에게 한 턴을 더 요청합니다.

## 기록을 믿을 수 있는 이유

- ledger는 사슬입니다. 모든 기록이 바로 앞 기록의 해시를 담고 있어 과거의 한 바이트만 바뀌어도 사슬이 끊깁니다. `g1 audit`은
  기록만으로 모든 receipt와 완료를 다시 계산합니다.
- 완료는 함수 하나입니다. G1이 직접 돌린 검사에서만 "완료"를 돌려줍니다. 모델의 의견을 포함한 다른 모든 입력은 "아니오"만
  말할 수 있습니다. 테스트가 입력의 모든 조합을 나열해, 실행된 증거 없이는 무엇도 "예"라고 말할 수 없음을 증명합니다.
- G1은 자신을 지킵니다. 모든 hook 항목에 G1 코드의 해시가 들어 있어 세션 중에 코드가 바뀌면 hook이 실행을 거부합니다. agy
  바이너리가 바뀌면 다시 측정할 때까지 완료를 보류합니다.
- G1은 위조된 역사를 알아챕니다. 프로젝트 밖에 anchor(닻), 곧 마지막으로 쓴 기록을 둡니다. 다른 곳에서 끝나는 ledger는 G1이
  아닌 무엇이 바꾼 것이고, 사용자가 `g1 repair`로 결정할 때까지 프로젝트는 잠깁니다.
- G1은 agent의 말을 증거로 쓰지 않습니다. agent의 transcript(대화 기록)를 읽는 목적은 하나, 도구 호출 수를 세어 자기 hook이
  모든 호출을 보았음을 증명하는 것입니다.

## 설치

```sh
git clone https://github.com/haamsuk-collab/im-not-gembyeong ~/src/g1
~/src/g1/bin/g1 install
```

agy에게 *"install G1 from https://github.com/haamsuk-collab/im-not-gembyeong"*라고 말해도 됩니다. agent가 같은 두 줄을
실행합니다.

설치기는 아래 파일을 쓰고 그 뒤로 계속 지킵니다.

| 파일 | 역할 |
|---|---|
| `~/.g1/g1.pyz` | G1의 코드(Python 표준 라이브러리만, 의존성 없음) |
| `~/.gemini/config/hooks.json`의 `g1` 그룹 | hook 항목 넷, 각각 코드 해시가 고정됨 |
| `~/.gemini/config/rules/g1.md`, `g1-instinct.md` | 항상 켜진 규칙 둘: 진입 규칙(권위의 순서, 다섯 의무, 동작 방식)과 본능 규칙(확인하거나 멈추기, 채널별 권위, 작업공간, 증거, 정직한 마지막 답) |
| `~/.gemini/config/rules/g1-work.md`, `g1-writing.md`, `g1-korean.md` | 상황별 규칙, agent가 코딩 전, 문서 작성 전, 한국어 작성 전에 읽음 |
| `~/.gemini/config/skills/g1/SKILL.md` | proposal 형식과 blocked, resume 보고서, agent가 필요할 때 읽음 |
| `~/.g1/workspaces/<id>/` | 프로젝트마다 ledger 하나, 첫 세션에 생성 |

G1은 프로젝트 안에는 아무것도 쓰지 않습니다. 누군가 hook 항목이나 규칙이나 skill을 바꾸면 다음 세션이 되돌립니다. 제거는
`~/src/g1/bin/g1 uninstall`이며 자기 항목만 지웁니다.

알아 두면 좋은 명령, 모두 선택입니다.

```sh
~/src/g1/bin/g1 status .      # G1이 아는 현재 프로젝트의 상태
~/src/g1/bin/g1 audit .       # ledger에서 모든 receipt와 완료를 다시 계산
~/src/g1/bin/g1 host-verify   # 새 agy 버전에서 probe를 다시 돌린 뒤
~/src/g1/bin/g1 repair .      # 무결성 lockdown 뒤: 무엇이 바뀌었는지 본 다음 --accept-ledger, --restore, --forget
~/src/g1/bin/g1 challenges .  # 검토 모델이 쓴 challenge 목록(아직 아무것도 실행하지 않음)
~/src/g1/bin/g1 challenges . --run   # 그 검사를 실행(다른 모델의 코드, 사용자의 권한으로)하고 판정을 기록
```

## 비용, 측정값

gemini-3.8-flash-high로 실제 agy 세션 137개(그중 하나는 Claude Opus 5.5가 검토자)에서 G1을 쟀습니다. 아래 숫자는 독립
oracle(판정기)이 냈습니다. 실행기가 최종 코드에서 원래 테스트를 다시 돌리거나 파일 트리를 직접 확인했고, G1도 agent도
결과를 제공하지 않았습니다.

| 질문 | 답 |
|---|---|
| G1이 agent를 느리게 하는가 | 아니오. 쓰기 도구 호출 75 ms, 모델 호출 96 ms, 읽기 전용 호출 0 ms. 검증은 턴당 한 번, 0.3~1초. |
| G1의 판정이 맞는가 | 46세션 중 46세션에서 G1의 "완료"가 독립 oracle과 일치. 거짓 완료 없음. |
| 일이 줄어드는가 | 쉬운 과제와 중간 과제: 토큰 17~24% 감소, 시간 23~32% 감소. 어려운 단일 세션 과제: 차이 없음. |
| 세션이 사라지면 | 세션을 죽이고 기록을 지운 뒤, 다음 세션이 토큰 39% 적게, 도구 호출 33번 대신 14번으로 마쳤음. 과제를 다시 찾아낼 필요가 없었음. |
| 두 번째 모델이 Flash가 놓친 것을 찾는가 | 한 번 끝까지: Flash의 라이브러리가 숨은 검사 44개 중 43개 통과. Claude Opus 5.5가 빠진 하나를 실패하는 검사로 73초 만에 증명, 거짓 보고 없음. 사용자가 수락한 뒤 Flash가 receipt 아래에서 수정(44/44). |
| 본능 규칙이 행동을 바꾸는가 | 모호하거나 불가능한 과제 여섯 개에서 Flash는 규칙이 있을 때 12세션 중 12세션, 없을 때도 12세션 중 12세션 멈추고 물었음. 이 부류에서는 측정되지 않고, 측정되는 비용도 없음. |

재지 못한 것: 보이는 테스트가 있는 자족적인 과제에서 Gemini 3.8 Flash는 60세션 동안 한 번도 실패하지도 거짓말하지도
않았습니다. 심판이 가장 필요한 경우, 큰 저장소와 며칠에 걸친 작업은 아직 이 데이터에 없습니다. 세부와 한계는
`docs/design.md` 14절과 `research/measure/`에 있습니다.

## 코드는 어떻게 검토되었는가

독립 리뷰 다섯 번이 코드를 읽었습니다. 각각 agy 안의 Gemini 3.8 Flash 세션에 서면 지침을 준 것입니다. 다섯 번째 전에는
Claude Opus 5.5와 Claude Fable 5.1이 같은 코드를 agy 밖에서 검토했습니다. 모든 지적은 검토자 자신의 스크립트로 재현한 뒤에
고쳤고, 모든 수정에는 지적의 이름을 붙인 테스트가 있습니다. 다섯 번째 리뷰는 아무것도 찾지 못했습니다. 지침, 보고서, 답변은
`research/review/`에 있습니다. 테스트는 126개입니다.

## G1이 하지 않는 것

- 모델을 더 똑똑하게 만들지 않습니다. prompt, 도구, agent의 루프를 바꾸지 않습니다.
- 두 번째 모델을 판사로 쓰지 않습니다. 판사는 "예"라고 설득당할 수 있지만 테스트는 그렇지 않습니다.
- agy의 기능을 대체하지 않습니다. 서브에이전트, 목표 모드, 병렬 시도는 그대로이고 G1은 결과만 검증합니다.
- 한 세션 안에서 셸로 G1의 파일을 전부 일관되게 다시 쓰는 agent는 막지 못합니다. G1 전체가 사용자 권한으로 돌기 때문입니다.
  이 잔존 위험은 `docs/design.md` 7.7절에 적혀 있습니다.

## 저장소 지도

```
src/g1/           핵심: ledger, contract, verify, complete, control, project, integrity, audit, install

tests/            테스트 126개: 사슬 끊김, 충돌 복구, 완료 함수, gate, canary, anchor, 자동 등록
bin/g1            명령줄 실행기
docs/             원칙, 설계, 호스트 계약
research/         불만 조사, 측정, probe, atom, A/B 실행, 리뷰
```
